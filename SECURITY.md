# Security policy

## Supported versions

The latest release receives fixes. sealift stays on `0.y.z` for now, and a fix ships as a new patch or minor release, never as a change to an existing tag.

## Reporting a vulnerability

Use GitHub's private reporting: **Security**, then **Report a vulnerability**, on this repository. Do not open a public issue for something you believe others could exploit.

Include the version, what an attacker needs, and the steps that show the problem. You get an acknowledgement within a week. A confirmed problem gets a fix in a release, and the advisory is published once that release is out.

## What sealift guarantees

- Every package in an archive matches the sha512 integrity the npm registry published for it. A mismatch stops the export.
- The sealift binary pins one Trivy release by version and by the sha256 of its tarball for each architecture. sealift installs a download only when its sha256 equals the pinned one. It never activates another version, and removes the others from the volume. Moving the pin takes a new sealift build.
- uv matches the sha256 the package index publishes for its wheel before sealift installs it. pnpm matches the integrity the registry in `SEALIFT_NPM_REGISTRY` publishes for its tarball. A project's target can name another pnpm or uv than the default target. No route installs a tool. An analysis installs the pnpm or uv version its target names, under the minimum release age and the integrity checks. Neither the start nor an analysis installs a release younger than the minimum release age, read from the publish time the registry or the index gives.
- `SEALIFT_NPM_REGISTRY` must be an `https` URL, or `http` on a loopback host. sealift refuses to start on a plain `http` registry elsewhere unless `SEALIFT_ALLOW_HTTP_REGISTRY` is `true`, and then logs a warning at each start.
- uv runs with `--no-build` and `--no-config`, so no package code runs on the connected side. A package with no wheel for the target is listed in the analysis, and the 409 that refuses the export of its set names it. When another package needs it and no wheel of its version installs on the target, the analysis fails and names it. uv reads no `UV_` or `PIP_` variable and resolves against the one index sealift names.
- A pip analysis records each package's wheel with the sha256 the index publishes, and fetches no wheel to choose it. For a package no file pins, it chooses among the files uploaded before the minimum release age, the files uv resolved that package from. A wheel added later to an older release, or a file the index gives no upload date, is never recorded for it.
- A pip export downloads each wheel the analysis recorded and checks it against the sha256 the package index published. A mismatch fails the export at once, with no retry. Each wheel is hashed again as it enters the archive, and the export never opens a wheel, so no package code runs on the connected side.
- A pip export's `manifest.json` is signed with the same key and the same scheme as an npm export's. An import that reads only npm archives refuses a pip archive by its format version: `sealift import` 0.6.2 exited 3 with `formatVersion is missing or not 2` on the pip archive of a run at commit 526302c, and published nothing.
- In the published image, sealift opens the files pnpm, uv and Trivy work with only when they are regular files, and creates its own files there only where none exists. A compromised tool cannot make it copy the private key, overwrite a file through a link at that name, or hold the job queue on a FIFO. A link at a directory on the way is still followed: the key stays out of reach, since sealift reads only fixed names and creates only new files there.
- sealift proposes no version younger than the minimum release age, 14 days by default, and holds the packages under it to the same age.
- At start, sealift downloads what an analysis needs, with no action from anyone. The pinned Trivy comes from GitHub and installs only when its sha256 matches the pin. That Trivy then fetches its vulnerability database from `mirror.gcr.io`. pnpm comes from `registry.npmjs.org` and must match the integrity the registry publishes. uv comes from `pypi.org` and `files.pythonhosted.org` under the uv checks above, and the start never forces a release younger than the minimum release age. pnpm and uv are the versions the default targets name. `SEALIFT_GITHUB_API`, `SEALIFT_NPM_REGISTRY` and `SEALIFT_PIP_INDEX` send those downloads to the addresses they name. After the start, sealift downloads nothing before you press Analyse or Seal. No route installs a tool or changes the policy.
- In the published image, pnpm, uv and Trivy run as a separate user that cannot read `private/`, which holds the private signing key and, on a volume from 0.7.0, its settings file.
- The policy file and its logo are deploy inputs, read once at start. sealift refuses to start on an unknown key, a value out of range, brand text with a control or formatting character, a contact address other than `https:` or `mailto:`, or a logo that is not a regular PNG or SVG file of at most 256 KiB, and names the key. `GET /api/instance/logo` serves the logo with `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox` and `X-Content-Type-Options: nosniff`, so a script in an SVG logo does not run when its address is opened.
- The archive is reproducible: the same selection built by the same sealift gives the same sha256. The reasons given for an export change the manifest only, never the archive.
- The signature of an npm export's manifest also covers its review: the project's CVE counts before and after the selection, each update, jump and kept dependency, each CVE the project keeps with its fixing versions, and every reason given. The import side reads the reasons and totals as the connected side signed them.
- sealift checks the reasons of every npm export on the server, whatever the client sends. A version outside its dependency's line, or a CVE that no version fixes in a version the archive holds, needs a reason, and the policy keys `review.majorJump` and `review.cveWithoutFix` set to `refuse` stop such an export whatever reason it holds. With the project tree, the check also reads the project's own scan. A CVE with no fix on a package no dependency's own scan names is placed by walking the shipped lockfile from the project's direct dependencies: each direct dependency whose tree holds the package needs a reason for it, and the review lists the CVE under that dependency with the package named. A package the walk cannot place refuses the export. A last check before signing refuses under `refuse` any CVE with no fix in the shipped scan, whatever the review lists.
- sealift checks the reasons of every pip export on the server, against the stored analysis, whatever the client sends. A package that left the major of the previous crossing, a CVE that no version fixes and a release its index yanked each need a reason that names the package. A missing, repeated or needless reason is refused with 400. With `review.majorJump`, `review.cveWithoutFix` or `review.yanked` set to `refuse`, such a set is refused with 409 whatever reasons it holds, and the refusal names the rule and the packages.
- The signature of a pip export's manifest covers its review: the CVE counts before and after, each changed pin, each major jump with its reason, each CVE the set keeps with its fixing versions or its reason, the unchanged count, and each yanked release with the index's reason and the reason given. Before signing, the export reads the review as the import would, and fails when the import would keep it out.
- The export request is bounded: at most 10,000 reasons, 10,000 selected dependencies and 10,000 dependencies per reason, each name at most 214 bytes. A request past a bound is refused with 400 naming it. Every request body under `/api` is capped whatever its `Content-Type`: a JSON body within 16 MiB, a project upload within 41 MiB (40 parts of at most 1 MiB), and a larger one is refused with 413. A body of any other type is refused with 415 before it is read.
- A reason's text follows one rule at export and at import, `archive.CheckReason`: 1 to 300 characters once trimmed, letters, marks, numbers, punctuation, symbols, the plain space and the no-break spaces U+00A0, U+202F and U+3000 only, within 4,800 bytes before reading. A control character, a line or paragraph separator, a bidirectional override or any other format character is refused, so a reason cannot break a line or reorder the text of a page, a table or a CSV that prints it. The export refuses a text over 1,200 characters before trimming, and signs the trimmed text. A refusal names the reason by its position and kind and never repeats its text.
- The import reads a review within the manifest's 16 MiB bound and checks each field's shape and length. A review it cannot read is kept out with the field at fault and no value from it, and the import checks and publishes the packages as before: a review never refuses an archive or changes what the import publishes. The export refuses a manifest over that bound, npm and pip alike.
- `sealift import` publishes nothing until the archive passes every check: its sha256 and size match `manifest.json` (and the sha256 you pass with `-sha256`, when you give one), the manifest's Ed25519 signature verifies with the key the import is configured to trust (`publicKeyFile`), every tarball matches its `shippedSha512`, and the listing has no extra, missing or oversized entry.
- The import never overwrites. A version Nexus already holds with other bytes fails with both digests, and the only exception is a copy that differs from the shipped one by the `publishConfig` that sealift removed.
- `sealift import` reads each wheel of a pip archive within fixed bounds: 100,000 entries, 1,024-byte entry names, 16 GiB declared unpacked, 1 MiB for `METADATA` and 64 KiB for `WHEEL`. It never unpacks a wheel or runs anything from it. It uploads the shipped bytes unchanged, and a wheel Nexus already holds with other bytes fails with both digests. A pip archive is refused before it is read when the settings name no pip repository, or when Nexus does not list that repository as pypi hosted.
- The import never turns TLS off, refuses redirects and warns when the Nexus URL is plain HTTP. Its credentials stay in memory: the password and the key are not written to the output, the report or an error.
- `sealift import-server` acts for a user only after the access token passes every check against the realm's keys: signature, algorithm, issuer, audience and expiry. A token signed by another key and a token with `alg` none each answered 401 in the lab. The user is the token's `preferred_username` claim alone; no forwarded header names one.
- The service reads and deletes only under `packages/npm/` in the bucket of the checked user, and never writes to MinIO. It removes an archive only after the import ended `complete` and its three objects, archive, manifest and signature, are unchanged.
- The import binary holds no Linux capability and is built to run under `--cap-drop ALL`. The image cannot set that flag: you set it in the compose file or on the `docker run` line, as [Deployment](docs/deployment.md#the-import-service) shows. Without it, the container keeps Docker's default capability bounding set, and the setuid binaries of the base image can use it.
- The import screens' files hold no user data, so `sealift import-server` serves them without a token and answers 404 for every other path outside `/api` and `/healthz`. Every answer of the service, files and API alike, carries a `Content-Security-Policy` that allows loads from the page's own origin only and forbids framing, plus `X-Frame-Options: DENY` and `X-Content-Type-Options: nosniff`. The page itself adds one style nonce to that policy: 16 random bytes drawn for each response, so the dialogs' styles load and no inline style without it does. The page is sent with `Cache-Control: no-store`, so no cache keeps a nonce. No flag or setting turns the token check off.
- Every export signs `manifest.json` with an Ed25519 key that sealift generates for its volume. The manifest names the archive's sha256 and every package's sha512, so one signature covers everything the import publishes. The import verifies the exact bytes it then parses, before it reads the manifest or the archive, with the one key in its settings. No key or digest carried by the archive, the manifest or MinIO changes the verdict: it only chooses the wording of a refusal. The check runs again on every retry.
- The service also checks each signature when it lists a user's folder, with the same key and the same code, before it reads anything else from the manifest. A project name, a date or a size from a manifest reaches a screen only once its signature verifies. The list reads each manifest within 16 MiB and each signature within 4 KiB, checks at most 50 manifests it has not checked before and reads at most 64 MiB in one list, and keeps at most 4,096 results, keyed by the bucket, the key and the ETags of both files. A key that a signature file names is shown only when it is 64 lowercase hex digits, and never trusted. The listing's verdict only words the screens: an import checks every byte again when it starts.
- The private key lives in `private/signing-key.pem` of the data volume, mode 0600, out of reach of the `tools` user. No API answer, log line, error, event, report or file of an export carries it, and a damaged key file stops sealift at start instead of being replaced by a new key.
- No HTTP route regenerates the key: the route of earlier releases answers 410 Gone. Regenerating takes `sealift signing-key regenerate`, run in the container or pod, so a page in another tab or a client of the port cannot break the import's trust. The command refuses to replace a key file that another user owns.
- The Helm chart installs the import service with its credentials in one Kubernetes Secret that you create: no value of the chart holds a credential and the chart never creates a Secret. It runs one container as a non-root user with a read-only root filesystem and every capability dropped.
- The service reads the access token from the one header that `token.header` names, and from no other: not `Authorization`, not a cookie, not `X-Access-Token` when another name is set. An absent or empty header answers 401 with the check `absent`. It refuses to start on a header named `Authorization`, `Cookie` or `Host`.
- The chart's NetworkPolicy admits the pod only from the ingress controller's namespace, only on the service's port. The chart refuses to render an Ingress without its sign-in annotations.
- The import screens show what Nexus answers as text, never as markup: its error pages show in the log only, and the uploader account it gives has control characters removed. A reason, a package name or a project name from a manifest is text the same way.
- Tokens (the GitHub token included), the MinIO secret key, the Nexus password and the private signing key stay out of logs, responses and stored records.
- In ephemeral mode (`SEALIFT_EPHEMERAL=1`), a project's id does not derive from its name, so no log line names the project, and the sweep logs counts only. Erasing a project deletes its directory, then the shared caches that recorded what it fetched as soon as no job is in flight. Every project idle for the configured delay is erased the same way. API answers carry `Cache-Control: no-store`, and the erase control clears the tab's stored selection.

## What it does not

- Ephemeral mode deletes files: it does not overwrite them. Without the overlay's RAM mounts, the disk can keep a deleted file's blocks. With them, a host with unencrypted swap can still write those pages to disk. The mode leaves the browser's history, its download folder and other tabs' storage alone, and it keeps Trivy, its database, the settings, the signing key and pnpm's update state under `home/`.

- The pinned sha256 covers the download. A directory of the pinned version already on the volume, such as one 0.7.0 installed and checked against the release's checksums file, stays in use and is not hashed again.
- The Trivy release lookup goes to the address in `SEALIFT_GITHUB_API` when you set it. That server supplies the download address of the pinned release: a mirror you do not control can delay Trivy, and cannot swap it, since the download must match the pinned sha256. sealift accepts only `https`, or `http` on a loopback host. `SEALIFT_GITHUB_TOKEN` goes to that address only, so a mirror receives the token.
- The signature shows that the manifest came from the holder of the private key. It does not show who asked for the export: anyone who reaches sealift's port can have any selection signed.
- There is no freshness check. An old archive with a valid signature stays importable until the key is regenerated.
- The reports (`summary.md`, `findings.csv`, `report.cdx.json`, `report.trivy.json`) are not signed. They inform the import side and are not covered.
- A reason is the word of whoever exported. The review names no person, since the connected side has no login, and the import does not check the review against the packages it publishes. A pip export compares its set with the previous crossing the analysis recorded, the latest done export of a pip project with the same name. Two unrelated projects that share a name compare with each other, and a renamed project starts with no previous crossing, so its export asks no jump reason.
- The yanked rule reads the yanked releases a pip analysis recorded. An analysis written by sealift 0.7.0 named them in its warnings only, so its export asks no `yanked` reason and `review.yanked: refuse` does not stop it. Its signed review lists no yanked release. A new analysis of the project records them, and the rule applies to its export.
- The import trusts the public key file its settings name. A key carried through the kiosk with the archive weakens the check: carry it by another channel and compare the public key sha256 on both sides. A lost volume or a regenerate means a new key to carry; sealift cannot import or restore a key.
- The minimum release age relies on pnpm's `minimumReleaseAge`, which the default pnpm 10.34.5 honours. An older pnpm, named by the policy file or a project's target, can ignore it for transitive packages.
- In a pip project, the pins of the requirements files are exempt from the minimum release age. A pinned release younger than it stays, and the analysis shows a warning with its upload date. The same holds for a wheel added later to a pinned release, when the target prefers it. A file of a pinned release that the index gives no upload date gets no warning. `--hash` options on a pin limit its wheel to the files they list.
- The image carries Debian's `python3` because uv needs an interpreter to start. It starts uv and builds nothing.
- pnpm's integrity and its publish time come from the registry `SEALIFT_NPM_REGISTRY` names, as does the integrity of every npm package sealift ships. A mirror you do not control can swap pnpm or a package. With `SEALIFT_ALLOW_HTTP_REGISTRY` set, anyone on the network path can do the same.
- A malicious package with no published CVE passes: Trivy knows only disclosed vulnerabilities. The minimum release age and the signals on each candidate reduce that risk; they do not remove it.
- sealift has no login. Anyone who reaches its port can run sessions, download archives and have any selection signed. No route checks the `Host`. Regenerating the key needs a shell in the container or pod. [Deployment](docs/deployment.md#access) shows how to keep it private.
- A Nexus repository that allows redeploy can be overwritten by another tool between the check and the upload. The runbook forbids another publish while an import runs.
- The chart's Secret is a plain Kubernetes Secret, base64 and no more: anyone who can read Secrets in the namespace can read the Nexus password and the MinIO keys.
- The NetworkPolicy takes effect only on a network plugin that enforces it, and the chart cannot tell. The runbook's checklist checks it from another namespace. Outgoing traffic stays open.
- The NetworkPolicy admits every pod of the ingress controller's namespace, not only the controller, unless `networkPolicy.ingressPodLabels` narrows it. An Ingress that someone in the cluster writes with an ExternalName backend or a snippet annotation can route to the service around the sign-in annotations. The service still checks every token, but the header's value then comes from the client. Ask the cluster's administrators whether ExternalName backends and snippet annotations are disabled in ingress-nginx.
- Whoever can write to the values repository can change the public key, the certificate authority, the Keycloak settings, the token header and the Nexus and MinIO addresses. The runbook asks for restricted, reviewed writes and a second look at those keys at each sync.
- The header's name grants nothing by itself, since every token is checked against the realm's keys. What keeps a client from choosing the token is that the ingress sets the named header from oauth2-proxy's answer on every request and drops the client's value. A header that the ingress does not set on every request leaves that choice to the client. ingress-nginx's annotations for this are not proven in the lab.
- The import writes no dist-tag and holds no delete right in Nexus. On Nexus 3.96.5 an upload can move `latest` forward to a newer stable version, which a bare `npm install` then gets. [The runbook](docs/runbook.md#worst-cases-on-the-shared-repository) lists what an import published, for an administrator to remove.
- The sha256 of an archive is only as trustworthy as the channel that carries it to the import side.
- Nexus may withhold who uploaded a version from an account with few privileges. A conflict then shows the day the copy reached Nexus and no account. Granting the import account more privileges to show it widens what a leaked import credential reaches.
- A valid token acts as its user. Anyone who holds one, for as long as it is valid and the realm accepts it, can list that user's archives and start imports in their name.
- The service's MinIO key reads every user's folder: the MinIO policy covers every `user-*` bucket, and the service alone keeps a request to the checked user's bucket. A flaw in the service reaches every folder.
- The service trusts the gateway to forward the token it checked. It reads the token from one header and cannot tell a gateway from a client that reaches it directly; keep its port off any network users can reach but the gateway.
